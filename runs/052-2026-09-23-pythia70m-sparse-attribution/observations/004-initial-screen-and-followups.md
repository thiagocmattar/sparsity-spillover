# Initial screen and bounded follow-ups

Question: can removing global packing create a complete sparse h/z consumer
that beats the retained routing at both moderate-kappa endpoints?

Method: `screen-002` operator-qualified all eight E/F configurations and their
no-skip controls, including metadata oracles and changing-input CUDA graphs.
All128 literal training blocks at each endpoint were then evaluated:64 for
development and64 for confirmation, five paired timing passes at each of12
sites. Selection required at least5% lower host latency in all four endpoint /
split cells. All gates, BF16 semantics and numerical bounds were unchanged.

Result: no configuration met promotion. At the closest z site (`z.1`), the
best warp configuration's worst-cell ratio was1.069 versus dense. At sparse
h sites the best ratios ranged1.258--1.378 versus retained C; at h.0 the best
ratio was2.485 versus dense. This is a negative result for these implementations,
not evidence that the activation structure cannot support a faster kernel.

Occupancy supports pursuing a different SIMT implementation: for example,
confirmation z.1 has mean16.83 /9.70 nonzeros per row at kappa .05 /.1, while
16-row unions contain45.45 /33.17 features. E's gathering, padded tensor-core
work and synchronization remain too expensive. F avoids union padding but scans
every32-feature chunk for each output tile and exposes small scalar weight loads
in its source. These are implementation hypotheses, not measured hardware
traffic or a definitive bottleneck attribution.

Exactly eight approved follow-up slots are used:

- Four vector-warp variants:4 or8 rows per CTA,4 or8 output values per lane;
  aligned64/128-bit weight loads and fixed512-output bounds.
- Four per-row CTA variants: compact support once in shared memory, reuse across
  all512 outputs, and2/4/8/16 values per thread. Parallel warp prefix sums build
  the complete unbounded support list. No truncation or threshold changes.

Their registry is `primitives_v3.py`; kernels are `followup_sparse.cu`. Original
implementations and attempts remain intact. `17_followup.py` pins the registry,
work counters and compiler evidence; `18_execute_v3.py` invokes unchanged
measurement scripts through that wrapper. Extra counters retain compact payload
reads and shared index/value writes. Matched no-skip paths scan/count identical
inputs and execute all features. Full-model conversion, gate and combine costs
remain included; component gains alone cannot establish the target.

The full bootstrap plus focused suite passed251 tests; Python compilation
passed. Target-GPU operator checks must still qualify these follow-ups.
