\subsection{When model-wide sparsity translates to speedup}
\label{sec:kernel-autoresearch}

A multiplication by zero cannot change a sum, but recognizing and skipping
it also takes time. $\Smodel$ measures the arithmetic exposed to zero
operands; lower latency requires an implementation that avoids more work
than it adds. GPUs perform groups of multiplications together, so isolated
zeros need not remove an execution step. Figure~\ref{fig:kernel-autoresearch}
shows the matrix instructions actually bypassed by our specialized kernel.
These percentages measure skipped instructions, not saved time.

Both the projection and attention paths inspect the current activations.
For FFN-down ($h$) and attention-output ($z$), the kernel checks which values
survive before reading the corresponding weights. Nearly empty rows can
then be projected using only their surviving contributions; empty groups
avoid both weight reads and multiplications. The matched 14M controls
locate the benefit from skipping in the projection path, with the code and
bypass counts pointing especially to $h$ and $z$ together. Their individual
time savings are not isolated. Speedup over native execution also includes
combining operations to reduce intermediate work, separately from skipping
zeros (Appendix~\ref{app:kernel-diagnostics}).

The current $QK/PV$ path checks for zeros after loading the operands.
It can omit multiplications, but has already paid for those reads and must
still normalize attention scores and produce the output. A zero score is
not a zero attention probability. The additional checks can therefore cost
more than the skipped arithmetic saves. In the matched 14M measurements,
disabling attention skipping makes the same models faster while leaving
projection skipping unchanged, even where $QK/PV$ bypass is substantial.

\textbf{This is a limitation of the tested implementation, not evidence that
attention sparsity is intrinsically unhelpful.} Shortcuts for zero queries,
broader zero-product detection and cheaper skipping decisions were explored,
but did not establish a reliable, numerically qualified attention benefit
(Appendix~\ref{app:kernel-results}). The frozen kernel is therefore not an
optimal execution strategy. Avoiding data movement earlier remains an
unresolved opportunity. The 70M bars establish instruction bypass under
the shape-specific port; they do not extend the 14M timing attribution.
